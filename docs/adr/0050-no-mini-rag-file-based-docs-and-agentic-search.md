# 0050. No mini-RAG over the docs corpus — file-based docs + agentic search stay

- Status: accepted
- Date: 2026-06-12
- Deciders: Horia
- Related: [RETROS 0006](../RETROS/0006-epic-0086-closeout-and-docs-system-review.md),
  [RETROS 0001](../RETROS/0001-quality-and-architecture-hardening.md) (A1 — CODEMAP),
  [CODEMAP.md](../CODEMAP.md), [CONTEXT.md](../CONTEXT.md), `scripts/codemap.sh`

## Context

The docs-as-operating-system now spans **~1.24 MB of markdown** (~300K tokens): 8 core
docs (~290 KB — CODEMAP 61K, CONTRACTS 69K, REGRESSIONS 46K, CONTEXT 28K, …), 50 ADRs,
92 issue files, 6 retros, 5 project skills. The question was whether agent sessions would
be better served by a **mini-RAG** (embed the corpus, retrieve top-k chunks per query)
than by the current "lots of files" approach — CLAUDE.md as a router, CODEMAP/CONTEXT as
hand-built indexes, and grep/glob/read agentic search over the rest.

## Considered options

- **Embedding mini-RAG (vector index over the docs).** Rejected. The costs are structural,
  not incidental: (1) **staleness** — this corpus churns on *every* merge (CODEMAP and
  INDEX regenerate per PR; issues get close-outs; REGRESSIONS grows), so the index is
  stale the moment it's built unless re-embedded in CI; (2) **infrastructure** — Anthropic
  ships no embeddings endpoint, so it means a third-party embedding provider, a vector
  store, a serving shim (MCP server or script), and chunking heuristics for
  table/code-heavy markdown — all new moving parts in a repo whose doctrine is "one fact,
  one home"; (3) **no retrieval-quality win here** — CONTEXT.md enforces a controlled
  vocabulary (forge, lane, meter, ledger…), and exact lexical search beats semantic
  similarity when the vocabulary is controlled: grep for `ledger` finds every ledger fact
  with zero false neighbors. Industry experience agrees: Claude Code itself dropped its
  early RAG/vector-db approach because iterative agentic search **outperformed** it while
  sidestepping index staleness, drift, and security exposure.
- **Bigger always-loaded context (concatenate the docs into CLAUDE.md).** Rejected — the
  corpus (~300K tokens) is loadable in a 1M window but would burn most of the budget on
  facts irrelevant to any one task. Progressive disclosure (router → index → targeted
  read) is the point of the current layout.
- **Keep file-based docs + agentic search, with the indexes as the "retrieval layer"
  (chosen).** The repo already has a hand-built, deterministic retrieval stack: CLAUDE.md
  routes (thin pointer), CODEMAP indexes symbols (generated, diff-reviewed, regenerated by
  `make codemap` so it is *never* stale at merge), CONTEXT defines terms once, and
  issues/INDEX.md tracks state. Below that, grep/glob give exact, always-fresh search over
  1.2 MB in milliseconds. Each retro (0001 A1, 0005) has confirmed windowed map-first
  reads keep audit sessions cheap.

## Decision

No mini-RAG. The retrieval layer for agents working in this repo is, in order:
**CLAUDE.md (router) → CODEMAP/CONTEXT/INDEX (generated or curated indexes) → grep/glob
(exact search) → windowed Read**. Invest in keeping the indexes regenerable and the
docs' headings/terms greppable (controlled vocabulary), not in embedding infrastructure.

## Revisit triggers

This is a corpus-size-and-shape decision, not a dogma. Revisit if any of these flip:

- the corpus outgrows what indexes + grep navigate well (≫1M tokens, e.g. multi-repo
  knowledge or imported external docs with *uncontrolled* vocabulary);
- queries become semantic rather than lexical ("what did we decide about X" where X is
  phrased unlike any doc term) *and* CONTEXT.md discipline can't close the gap;
- a first-party, zero-maintenance retrieval primitive (e.g. server-side search over
  attached files) makes the infrastructure cost ~0.

## Consequences

- No new infra; `make codemap` and the INDEX-regen discipline remain the freshness
  mechanism, and doc headings/terms stay the search keys — keep writing them greppable.
- Sessions keep paying the (small) token cost of iterative search instead of a one-shot
  retrieval; retros to date show this cost is bounded by map-first windowed reads.
