Cookbook

Process knowledge packaged as doc-based software: versioned, installable into any repo (new, old, or mid-flight), self-checking, and updatable — extracted from the Copilot-sdk process stack, distributed through your own plugin marketplace.

Manifest + templates + scripts + evals. The unit of versioning (SemVer) and dependency.

→
repo statedurable, agent-agnostic

Docs, CI guards, scripts, lock file — installed into the repo. Works with no plugin present, and for any agent (CLAUDE.md and AGENTS.md pointers).

Key distinction: a skill/plugin is session-scoped and leaves no trace. A recipe installs durable state into the repo. They compose — the recipe ships as a plugin, but its product is repo content.

3 · Anatomy — a recipe is software made of docs
recipes/quality/ ├─ recipe.yaml ← the interface │ name · version (semver) │ requires: [core] + facts │ {test_cmd, lint_cmd, ci…} │ provides: files · scripts · CI │ tiers: S / M / L file sets │ min_model: per step ├─ templates/ ← implementation │ REGRESSIONS.md.tmpl │ ci-snippet.yml.tmpl ├─ scripts/ ← determinism │ doctor.sh guard.sh └─ evals/ ← the tests (≥3) fixture → install → assert target-repo/.recipes/lock.json {name, version, tier, answers:{...}, installedAt}
Interface → requires

Repo facts the recipe needs bound (test command, CI provider, language) and recipes it depends on. Facts are never copied — asked at install or harvested.

Tests → doctor.sh

Deterministic conformance: "CLAUDE.md points at CONVENTIONS · no feature-branch push trigger · every fixed bug has a guard test." Your check-workflows.sh, generalized. Wired into lint + CI.

Package state → lock.json

The Copier insight: record version + answers in the repo. Without it, every re-application is a blind overwrite. With it, updates are 3-way merges.

Releases → SemVer per recipe

Update a fleet repo = diff lock vs latest → agent does the semantic 3-way merge (old template / repo's copy / new template) → PR. Never auto-applied.

4 · Install & update flow — /adopt-recipes
1

Inventory

Detect language, build system, CI, existing docs. Deterministic script, runs on any repo.

2

Propose

Profile + tier + answers, confirmed with you. greenfield → full scaffold, empty-but-structuredbrownfield → HARVEST: generate CONVENTIONS from existing CI/Makefile/CONTRIBUTING — never clobber

3

Apply in dependency order

core → quality/loop/issues/release/contracts → bindings. Gaps become flagged backfill checklist items (the proven "ADR needed (backfill)" pattern) — adopt incrementally, never block on completeness.

4

Lock + wire enforcement

Write .recipes/lock.json; wire doctors into make lint / CI — enforce with hooks, not memory.

5

Doctor

Conformance report. Divergence from upstream is a flag, not an error — repos legitimately fork rules; a fork becomes a local decision note or an upstream contribution.

↻

Update loop — /update-recipes

Lock vs latest → semantic 3-way merge → PR → human review. The fix for scaffold drift: improve the recipe once, every repo can pull it.

Breaking a provided contract requires the same ceremony everywhere: decision note + version bump + consumer notification. Each repo's CONTEXT defines only local terms and points up to the shared glossary — one fact, one home, scaled to N repos.

7 · Model portability — why this makes cheaper models execute flows correctly

determinism → scripts

  • base verification, next-item picking, doctors, guards — executed, not interpreted
  • a step moved into a script is a step a small model can't get wrong

structure → checklists

  • every workflow is a checklist with a testable termination condition
  • weak models fail on ambiguity, not length

certification → evals

  • ≥3 runnable evals per recipe, run per model tier
  • min_model recorded in the manifest — "can a smaller model run this loop here?" gets a measured answer, not a vibe
